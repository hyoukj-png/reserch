# 디자인 시스템 & 컴포넌트 분석

흩어진 디자인 토큰과 스크린샷을 **복제 가능한 디자인 시스템**으로 재구성한다. 핵심 산출은 (1) synthesizer용 `_workspace/design_findings.md`, (2) 사용자용 `05-components.md`다.

## 왜 이렇게 하는가

수집 데이터는 "HEX 12개, 폰트 3개" 같은 **원자 단위**로만 존재한다. 리뉴얼·복제에 필요한 건 "primary 1색 + 회색 4단계로 구성된 절제된 팔레트, 8px 그리드 간격, 라운드 카드 + 고대비 버튼"이라는 **시스템과 패턴**이다. 토큰을 의미로 묶고, 스크린샷에서 토큰만으로는 안 보이는 레이아웃·분위기를 읽어내는 것이 이 스킬의 일이다.

## 입력 읽기 순서

1. **`10-design-tokens-structured.md` (있으면 1차 근거)** — Playwright가 실제 렌더된 요소의 `getComputedStyle`을 전수 수집해 결정론적으로 토큰화한 결과. **이미 군집화된 primary/accent/neutral 팔레트, 타입·간격·radius·shadow 스케일, 모션 토큰, WCAG 대비, 디자인 스코어(A–F)**가 들어 있다. 정적 regex보다 정확하므로 컬러/타이포/간격 분석의 출발점으로 삼는다. 기계가독 원본은 `tokens/tokens.dtcg.json`·`tokens/tokens.tailwind.js`·`tokens/tokens.css`.
2. `03-design-tokens.md` — 정적 수집(CSS 변수 컬러, inline HEX, 감지 폰트). `10-`이 없을 때의 대체 근거이자, CSS 변수 *명명*(`--primary` 등 의미) 보강용.
3. `screenshots/pc/`, `screenshots/mobile/` — **`Read`로 이미지를 직접 열어 본다.** 레이아웃 그리드, 히어로 구성, 카드/버튼 스타일, 반응형 변화를 관찰.
4. `06-interaction.md` / `09-runtime-interactions.md` — 슬라이더/탭/모달 등 동적 컴포넌트 존재 근거
5. `pages.json` — 페이지별 구조 참고

> ⚠️ `10-`(computedStyle)과 `03-`(정적 regex)이 어긋나면 **`10-`을 신뢰**한다 — 선언된 변수가 아니라 실제 렌더에 쓰인 값이 진실이다([[collection-misses-loaded-vs-used-libs]]와 같은 결).

스크린샷이 없으면 토큰 기반 분석만 하고 "⚠️ 스크린샷 없음 — 레이아웃은 토큰 기반 추정"을 명시한다.

## 분석 단계

### 1. 컬러 팔레트 군집화
**`10-`이 있으면 거기 군집된 primary/accent/neutral을 그대로 채택**하고, CSS 변수명(`03-`)으로 의미 근거만 보강한다. `10-`이 없으면 나열된 HEX를 직접 역할로 묶는다:

| 역할 | 컬러 | 근거 |
|------|------|------|
| Primary | `#1A3B8C` | `10-` interactive 배경 군집 / `--primary` |
| Neutral 스케일 | `#FFF`→`#222` 4단계 | `10-` neutral 군집 |
| Accent | `#FF6B00` | `10-` accent / `--point` |

명도/채도로 스케일을 추정하고, 팔레트 성격을 한 줄로(예: "저채도·고대비·모노톤 중심"). **`10-` 또는 `03-`에 실재하는 값만** 쓴다(QA 정합성 통과). `10-`의 디자인 스코어(A–F)·WCAG 대비 결과가 있으면 톤 요약·접근성 코멘트에 인용한다.

### 2. 타이포그래피 시스템
감지된 폰트를 역할(제목/본문/강조)로 배치하고, 스크린샷에서 크기 위계를 관찰해 스케일을 추정한다. 웹폰트인지 시스템폰트인지, 한글/영문 폰트 구분.

### 3. 레이아웃 & 간격
스크린샷에서 그리드 구조(컬럼 수), 여백 밀도(빽빽함/여유로움), 컨테이너 최대폭, 반응형 변화를 읽는다. 토큰만 있으면 간격 변수에서 추정.

### 4. 컴포넌트 카탈로그 (05-components.md의 핵심)
재사용 UI 단위를 식별하고 각각 기술한다:

| 컴포넌트 | 스타일 특성 | 출현 위치 | 복제 난이도 |
|----------|------------|----------|------------|
| Primary 버튼 | 라운드 4px, 고대비, 호버 시 채움 | 전역 | 쉬움 |
| 제품 카드 | 그림자, 이미지 상단, 호버 확대 | `/products` | 보통 |
| 히어로 슬라이더 | 풀블리드, Swiper | `/` | 어려움(라이브러리) |

대상 컴포넌트: 버튼, 카드, 내비게이션, 히어로, 폼, 슬라이더, 푸터, 모달 등 관찰되는 것.

> **⚠️ Swiper/슬라이더 역할은 클래스명이 아니라 소속 섹션으로 확정.** `09-runtime-interactions.md`의 **"섹션별 인터랙션 인벤토리"**에서 각 Swiper가 **어느 섹션·슬라이드 몇 장**인지 확인하고 역할을 정한다. 클래스명만으로 추측 금지 — 과거 사례: `main_view`를 이름만 보고 "히어로 슬라이더"로 오귀속했으나 실제는 sec04 둘러보기 시설갤러리(11장)였고, 히어로는 Vimeo 단독(슬라이더 없음). **스크롤 연동 장식 모션**(예: `.big_size` 워드마크의 가로 패럴랙스)은 인벤토리의 `big_size` 컬럼 + "스크롤 연동 요소" 섹션으로 확인해 컴포넌트/모션에 반영한다.

### 5. 디자인 톤 한 줄 요약
세 영역을 종합한 인상. 예: "미니멀·고대비·여백 중심의 신뢰감 있는 B2B 톤". synthesizer가 사이트 정체성 정의에 직접 쓴다.

## 출력 1: `_workspace/design_findings.md`

```markdown
# 디자인 발견 (design_findings)
## 1. 컬러 팔레트 {역할별 군집 표}
## 2. 타이포 시스템 {폰트·역할·추정 스케일}
## 3. 레이아웃 & 간격 {그리드·여백·반응형}
## 4. 컴포넌트 카탈로그 {표}
## 5. 디자인 톤 한 줄 요약
```

## 출력 2: `05-components.md` (사용자용)

한국어 컴포넌트 카탈로그. 컴포넌트별 스타일·용도·복제 난이도를 상세히. 스크린샷을 봤다면 시각적 특징을 구체적으로 기술(색·모양·여백·인터랙션). 기술 용어는 영문 유지.

- [ ] `10-design-tokens-structured.md`가 있으면 그 군집·스케일·스코어를 1차 근거로 썼는가?
- [ ] 팔레트의 모든 컬러가 `10-` 또는 03-design-tokens에서 확인되는가?
- [ ] 컴포넌트마다 복제 난이도를 매겼는가?
- [ ] 디자인 톤 한 줄 요약을 작성했는가?
- [ ] 두 출력 파일 모두 생성했는가?
