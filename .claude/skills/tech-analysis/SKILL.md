# 기술 스택 & 성능 분석

수집된 원시 기술 데이터를 **리뉴얼·벤치마킹에 쓸 수 있는 인사이트**로 변환한다. 핵심 산출은 (1) synthesizer가 소비할 `_workspace/tech_findings.md`, (2) 사용자용 `07-performance-a11y.md` 두 가지다.

## 왜 이렇게 하는가

수집 스크립트는 "React 감지", "슬라이더 3개" 같은 **사실의 나열**만 만든다. 리뉴얼 의사결정에 필요한 건 "이 기술이 **어느 페이지에서 어떤 경험을 위해** 쓰였고, **유지/교체/도입** 중 무엇이 맞는가"라는 **판단**이다. 이 간극을 메우는 것이 이 스킬의 존재 이유다.

## 입력 읽기 순서

1. `00-summary.md` / `analysis_data.json` — 사이트 규모 먼저 파악
2. `02-tech-stack.md` — 카테고리별 탐지 기술 (표 형식)
3. `06-interaction.md` — 슬라이더/탭/모달/폼/애니메이션 수량
4. `pages.json` — 기술→페이지 매핑의 **근거 데이터**. URL·depth·구조가 들어있다.
5. `lighthouse.json` — 있으면 성능/접근성/SEO 점수. 없으면 정적 신호로 대체.

입력 파일이 없으면 1회 재확인 후, 없는 채로 진행하고 발견 문서에 누락을 명시한다.

## 분석 단계

### 1. 기술 스택 판단 표
각 탐지 기술을 카테고리(프레임워크/UI라이브러리/CMS/분석/호스팅/폰트 등)로 묶고, **벤치마킹 판단**을 붙인다.

| 판단 | 의미 | 예 |
|------|------|-----|
| 유지 가치 | 차별화되거나 잘 맞는 선택 | 고급 WebGL, 잘 쓴 디자인 시스템 |
| 교체 검토 | 노후/과한/비효율 | 구형 jQuery 의존, 무거운 빌더 |
| 도입 검토 | 없지만 있으면 좋을 것 | 이미지 최적화, 분석 도구 부재 |

흔한 기술과 차별화 기술을 반드시 구분한다. "차별화"가 벤치마킹의 핵심 후보다.

### 2. 기술→페이지 매핑 (가장 중요)
벤치마킹 레시피의 토대다. 각 의미 있는 기술에 대해:

| 기술 | 핵심 적용 경로 | 근거 | 비고 |
|------|---------------|------|------|
| Swiper | `/`, `/products` | 06-interaction 슬라이더 N개 + pages.json 해당 경로 | 히어로·상품 회전 |

**근거 없는 매핑은 쓰지 않는다.** pages.json·06-interaction에서 확인되는 것만 단정하고, 추정이면 "추정"으로 표시한다. 이 규율이 QA의 환각 검증을 통과하는 길이다.

### 3. 인터랙션 패턴 요약
동적 요소를 사용자 경험 관점으로 묶는다. "탭 5개, 모달 2개"가 아니라 "제품 상세는 탭 기반 정보 구성, 문의는 모달 폼". 부재도 해석한다(애니메이션 라이브러리 없음 → 정적·경량 지향).

> **⚠️ "0개"는 의심하라 — 정적 수집의 맹점.** `06-interaction.md`는 정적 HTML 정규식 기반이라 **JS로 열리는 모달·탭·아코디언을 놓친다.** "모달 0개/폼 0개"가 나와도 그대로 믿지 말고, 다음 숨김 콘텐츠 신호를 점검하라: (a) `javascript:` href나 `onclick`/`after_on()` 같은 트리거 함수, (b) `display:none`으로 숨겨진 `.modal`/`#modals_*` 컨테이너, (c) 본문이 비정상적으로 빈약한 페이지(핵심 콘텐츠가 모달/탭 뒤에 있을 수 있음). **먼저 `pages/_modals.md`를 확인하라** — 수집 스크립트가 모달/숨김 콘텐츠를 자동 복구해 이 파일에 저장한다(있으면 1차 인터랙션·콘텐츠 소스). 없는데 위 신호만 보이면 tech_findings에 "정적 수집이 놓쳤을 가능성 — 모달 콘텐츠 추가 수집 권장"을 명시하고, `_supplement/`에 수동 보충 HTML이 있으면 그것을 반영하라. `00-summary.md`/`06-interaction.md`의 모달 트리거·숨김 블록 수치도 참고하라.

> **⚠️ 인터랙션 "내부 동작"은 런타임 근거 없이 단정하지 말 것.** 자가진단 위젯(예/아니오 설문·카운트업 타이머 등)의 **진행 방식(동시 노출 vs 순차 분기), 진행바 유무, 상태머신 구조, 결과 임계값**은 `09-runtime-interactions.md`의 **"자가진단 위젯" 섹션 실측값을 1차 정답으로** 삼는다. 거기서 `진행바 없음(실측)`·`순차분기 없음(실측)`이라고 나오면 그대로 반영하고, **추출기가 못 본 부분은 "미확인(추정)"으로 표기**한다. 과거 사례: 검진설문이 정적 추출에서 `survey=0`으로 오탐되자 분석가가 "상태머신+진행바+결과 임계값(0~1/2~3/4~5)"을 **창작**했으나 실제는 5문항 동시 토글이었다. **DOM에 없는 동작을 만들어 내면 복제본이 원본과 달라진다.**

### 4. 성능/접근성
- **lighthouse.json 있을 때:** performance/accessibility/seo/best-practices 점수와 주요 지표(LCP/CLS/TBT)를 뽑아 **체감 언어**로 번역한다. "LCP 4.2s → 모바일에서 첫 화면이 느리게 뜸".
- **없을 때:** 정적 신호로 추정 — 이미지 수/최적화 여부, 스크립트 수, 외부 리소스. "측정 데이터 없음, 정적 추정"을 명시한다.
- 접근성: alt 텍스트, 시맨틱 태그, 폼 레이블 단서를 pages 데이터에서 점검.

## 출력 1: `_workspace/tech_findings.md`

synthesizer가 바로 소비하는 구조화 문서. 다음 4블록을 반드시 포함:

```markdown
# 기술 발견 (tech_findings)
## 1. 기술 스택 판단
{카테고리·기술·벤치마킹 판단 표}
## 2. 기술→페이지 매핑
{기술·경로·근거 표}
## 3. 인터랙션 패턴
{경험 관점 요약}
## 4. 성능/접근성 요약
{점수 또는 정적 추정 + 한계 명시}
```

## 출력 2: `07-performance-a11y.md` (사용자용)

한국어 리포트. 기술 용어는 영문 유지. 구성: 성능 점수/지표 → 접근성 이슈 → **개선 우선순위**(임팩트×난이도). lighthouse가 없으면 그 사실과 정적 추정 한계를 서두에 명시.

- [ ] 두 출력 파일 모두 생성했는가?
